# Analysis: why Axylo is 98 KiB and how to get it to its size budget

You are an independent analyst from a different provider than most of this code's authors. Read-only: do not create, edit or delete files. Put everything in your final message. Node, TypeScript and esbuild are installed (no network); you may run esbuild in memory (`write: false`, `metafile: true`) and write throwaway scripts to stdout only. Say for each number whether you measured it (and how) or estimated it.

## The problem

Axylo is a browser charting library (`packages/axylo/src`; product in `docs/02-product-spec.md`, design in `docs/03-plan-typescript-release.md`). Criterion DX7 sets provisional size targets, minified and gzipped, CSS included: 40 KiB for everything, 25 KiB for a page that imports only `line`, 2 KiB for the React adapter. The first measurement on the packed distribution (`node scripts/size.mjs --no-build` reproduces it; details in `reviews/2026-11-18/impl/wp/dist.report.md`) is:

- everything: 97.75 KiB (283 kB minified)
- line only: 97.61 KiB: chart types do not tree-shake at all (137 bytes saved)
- `validate` only: about 20.7 kB gzipped (from source)
- by directory, minified: data 24%, core 16%, dom 13.5%, theme 9%, render 7%, lookup 6%, layout 4%, scale 4%, view 4%, scene 3%, diagnostics 3%, reader 2%, format 2%

For comparison, Phase 1 measured other libraries the same way (`docs/01-landscape.md`, section 1.4): read it for what uPlot, Chart.js and the others weigh, and what they do and do not include.

The library was written by several agents working module by module against fixed contracts, with correctness and review as the priority; nobody has optimised for size yet. The owner needs to know what a realistic size is and what it costs to get there, before deciding whether the targets stand.

## What to produce

1. **Where the bytes are, at function level.** Using esbuild's metafile and your own measurements (for example bundling with a module or function stubbed out to see the gzipped difference), list the largest contributors: which functions, tables and strings. Separate: code every chart needs; code only one chart type needs; code only streaming, zoom, the table, the tooltip, the canvas renderer, or the compact variant needs; development-only text that reaches the production file; duplicated logic across modules (several authors may each have written their own clamp, binary search, date arithmetic, text escaping, deep-equal); verbose patterns that minify badly (long property names on internal objects that cannot be mangled, classes with many methods, string-keyed tables, repeated error messages, enum-like objects, defensive validation repeated at several layers).
2. **Why nothing tree-shakes.** Trace the import graph from `line` in `packages/axylo/src/index.ts` and show exactly which references pull in the code for area, bar, scatter, donut, the point and donut stores, both renderers and the rest. Then design the smallest restructuring that makes `import { line }` carry only what a line chart needs, keeping the public API in `packages/axylo/src/public.ts` unchanged: what moves where, which registries or switch statements become per-type composition, what the script-tag build still bundles. Estimate the line-only size after it, and say how you estimated it (ideally by building a scratch entry in memory that composes only the line path, if the code allows it without edits).
3. **A ranked list of reductions** for the "everything" bundle: for each, the bytes saved (gzipped, measured where possible), the risk to behaviour (which acceptance criteria in the spec it touches), and the effort. Include at least these candidates and give a verdict on each: shipping one mark renderer by default and loading the other only when asked (decision `docs/decisions/0002-mark-renderer.md` is provisional; say what each renderer costs); diagnostic message text in production (spec 3.5 and F12 require the codes and the visible note in every build: what text can be development-only without breaking that); the stylesheet as a string inside the JavaScript as well as a file; the streaming stores versus static normalisation; the table and the keyboard layer loaded on first use (dynamic import: what it does to the script-tag build, to CSP, and to "works without configuration"); the scatter grid; time-zone and calendar arithmetic versus `Intl`; typed-array growth helpers; anything written twice.
4. **What the realistic numbers are.** Three figures with your confidence in each: what "everything" and "line only" can reach with restructuring only (no behaviour removed); what they can reach if lazy loading of table, keyboard layer and second renderer is allowed; and what would have to be cut from the product to reach 40 and 25. If the targets are not reachable without removing things the spec requires (the accessibility layer, the table, diagnostics, three time kinds, streaming), say so plainly and propose targets you can defend, with the comparison to what the Phase 1 libraries ship for the features they have.
5. **A work plan**: ordered steps, each with owner module, expected saving, and the test that proves behaviour did not change (the repository has 1,216 unit tests including 494 acceptance tests, plus browser suites; `acceptance/README.md`). Put the tree-shaking restructuring first if it is the largest structural win.

Be concrete: file and line for every claim about code, numbers for every claim about size. No general advice about bundle size. End with the five largest single wins in one table.
